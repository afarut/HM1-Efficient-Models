## 1. Условия и размеры

Вход: B×3×S×S, S кратно 16. FP32, eval(), inference_mode(), без градиентов. Conv без bias, Linear с bias; BatchNorm в заданной таблице слоёв отсутствует. ReLU inplace. MAC = 2 FLOPs. Сравнения MaxPool/ReLU не включаю в число арифметических FLOPs.

| Слой | Выход на один объект | Число весов | MAC-FLOPs на батч |
|---|---|---:|---:|
| Conv 7×7, 3→32, stride 2 | 32×(S/2)² | 4 704 | 2 352 BS² |
| MaxPool 3×3, stride 2 | 32×(S/4)² | 0 | 0 (сравнения) |
| Conv 5×5, 32→64 | 64×(S/4)² | 51 200 | 6 400 BS² |
| Conv 3×3, 64→128, stride 2 | 128×(S/8)² | 73 728 | 2 304 BS² |
| Conv 1×1, 128→256 | 256×(S/8)² | 32 768 | 1 024 BS² |
| Conv 3×3, 256→256, stride 2 | 256×(S/16)² | 589 824 | 4 608 BS² |
| Conv 1×1, 256→512 | 512×(S/16)² | 131 072 | 1 024 BS² |
| GlobalAvgPool | 512 | 0 | 2 BS² |
| Linear 512→256 | 256 | 131 072 + 256 bias | 262 144 B + 256 B |
| Linear 256→100 | 100 | 25 600 + 100 bias | 51 200 B + 100 B |

После каждой свёртки и первой Linear стоит ReLU. Всего 17 вычислительных операторов: 6 Conv + 7 ReLU + MaxPool + GAP + 2 Linear. Flatten — изменение представления без копирования.

## 2. FLOPs(S,B)

Для свёртки F_conv = 2 B H_out W_out C_out C_in k².

Сумма свёрток: F_conv,total = 17 712 BS².

Для GAP на каждом из 512 каналов n=(S/16)² элементов: n−1 сложений и одно деление, всего n операций. Значит F_GAP = 512 B(S/16)² = 2 BS².

Две Linear: 2B(512·256 + 256·100) = 313 344 B; bias добавляет (256+100)B = 356B.

**FLOPs(S,B) = B(17 714 S² + 313 700).**

Например, S=224, B=1: 889 131 364 FLOPs ≈ 0.889 GFLOPs.

Profiler PyTorch считает Conv/Linear MACs; при сравнении с ним исключаю GAP и bias: F_profiler = B(17 712 S² + 313 344).

## 3. Memory(S,B)

Число параметров P = 1 040 324, значит веса занимают W = 4P = 4 161 296 байт.

Измеряем пик torch.cuda.max_memory_allocated() за один forward. Перед forward сбрасываем peak stats. В пик входят уже размещённые веса и вход. Внешняя переменная x сохраняет исходный вход до конца forward. Выходы предыдущих запусков удалены.

Пиковые живые тензоры около первого MaxPool:

- исходный вход: 3BS² FP32 → 12BS² байт;
- вход MaxPool (выход Conv1): 32B(S/2)² = 8BS² FP32 → 32BS² байт;
- выход MaxPool: 32B(S/4)² = 2BS² FP32 → 8BS² байт;
- временные индексы MaxPool: 2BS² int64 → 16BS² байт.

Итого **Memory(S,B) ≈ 4 161 296 + 68 BS² байт.**

В этом выражении нет калибруемых коэффициентов. Без временных индексов было бы 52BS² + W. Индексы могут выделяться внутри PyTorch даже при return_indices=False; конкретный backend влияет на реализацию.

Граница применимости: фактический peak включает временный workspace выбранного cuDNN-алгоритма и округление размера блоков аллокатором. Они не определяются одной архитектурой. Поэтому формула — аналитическая оценка при указанных допущениях, а не обещание точного равенства. Для других слоёв при этой архитектуре объём живых тензоров меньше. Memory_reserved и память CUDA-контекста не равны max_memory_allocated.

Грубый прогноз OOM: Memory(S,B) > полная память одной GPU. Обратное не гарантирует успех: доступная память меньше полной, есть workspace и фрагментация. Использование двух T4 не объединяет их память: модель работает на cuda:0.

## 4. Bytes moved Q(S,B)

Это модель логического трафика, не аппаратный счётчик DRAM. Каждый оператор читает вход и веса один раз и записывает выход один раз. Кэш, повторные чтения и внутренний workspace не учитываются. Для inplace ReLU всё равно есть чтение и запись.

Conv/Linear: Q_i = 4(B A_in + B A_out + W_i), где A — элементы активации на объект, W_i — число параметров слоя с bias, если он есть.

ReLU: Q_i = 8 B A_i.

MaxPool: Q_pool = 4B(8S²+2S²) + 8B·2S² = 56BS², включая запись int64 индексов.

GAP: Q_gap = 4B(2S²+512).

После суммирования всех 17 операторов:

**Q(S,B) = 380 BS² + 8 592 B + 4 161 296 байт.**

Для полностью явной послойной формулы обозначим X=BS². В порядке выполнения значения (F_i,Q_i) следующие:

| i | Оператор | F_i | Q_i, байт |
|---:|---|---:|---:|
| 1 | Conv1 | 2352X | 44X+18816 |
| 2 | ReLU1 | 0 | 64X |
| 3 | MaxPool | 0 | 56X |
| 4 | Conv2 | 6400X | 24X+204800 |
| 5 | ReLU2 | 0 | 32X |
| 6 | Conv3 | 2304X | 24X+294912 |
| 7 | ReLU3 | 0 | 16X |
| 8 | Conv4 | 1024X | 24X+131072 |
| 9 | ReLU4 | 0 | 32X |
| 10 | Conv5 | 4608X | 20X+2359296 |
| 11 | ReLU5 | 0 | 8X |
| 12 | Conv6 | 1024X | 12X+524288 |
| 13 | ReLU6 | 0 | 16X |
| 14 | GAP | 2X | 8X+2048B |
| 15 | Linear1 | 262400B | 3072B+525312 |
| 16 | ReLU | 0 | 2048B |
| 17 | Linear2 | 51300B | 1424B+102800 |

Арифметическая интенсивность I = FLOPs / Q, единицы FLOPs/байт. Один и тот же элемент может учитываться несколько раз, если его обрабатывают разные операторы.

## 5. Latency(S,B,θ)

Обозначим τ — эффективную стоимость запуска оператора, C — эффективную производительность в FLOPs/с, D — эффективную пропускную способность в байт/с.

**T(S,B;θ) = 17τ + Σᵢ₌₁¹⁷ max(F_i(S,B)/C, Q_i(S,B)/D), θ=(τ,C,D).**

F_i и Q_i определены выше; для ReLU/MaxPool F_i=0 по принятому определению FLOPs. Это также означает, что стоимость сравнений приближённо поглощается трафиком и эффективными параметрами.

Малые задачи: доминирует 17τ, launch-bound. При F_i/Q_i < C/D оператор memory-bound; при F_i/Q_i > C/D — compute-bound. У разных слоёв одной сети режимы могут различаться. Три режима — гипотеза модели, а не обязательный результат измерений.

T_real — медиана 9 отдельных синхронизированных измерений perf_counter после 3 прогревов. Это host wall-clock forward, включая Python и синхронизацию, без генерации входа и передачи CPU→GPU.

Подбор: минимизируем Σ_train (log T_pred − log T_real)² по положительным τ,C,D. Это даёт сопоставимый вес малым и большим задачам. Train — только базовая сетка. Все дополнительные случайные S/B — validation; параметры по ним не подбираются.

## 6. Energy(S,B,θ_E)

Энергию считаем для всей одной GPU, без вычитания idle. На одной конфигурации выполняем N forward подряд, измеряем энергию серии и делим на N. N выбираем так, чтобы серия длилась примерно 1.2 секунды (N рассчитано по latency; фактическое окно может быть короче). Предпочитаем аппаратный накопительный NVML energy counter; если его нет, интегрируем мощность методом трапеций с опросом каждые 20 мс.

E_real = (E_counter,end − E_counter,start)/N, либо E_real ≈ (1/N) Σ_j (P_j+P_(j+1))/2 · (t_(j+1)−t_j).

**E(S,B;θ_E) = α FLOPs(S,B) + β Q(S,B) + P₀ T(S,B;θ).**

То есть **E = α B(17 714 S²+313 700) + β(380 BS²+8 592B+4 161 296) + P₀[17τ+Σ_i max(F_i/C,Q_i/D)].**

α имеет единицы Дж/FLOP, β — Дж/байт, P₀ — Вт. Коэффициенты неотрицательные и калибруются только на train через least squares относительной ошибки. θ из предыдущего пункта фиксирован. Слагаемое P₀T моделирует зависящие от времени затраты; αF и βQ — динамические затраты.

Ограничения: частота/температура GPU, дискретность датчика, возможные посторонние процессы и сильная корреляция F и Q. Поэтому α,β,P₀ нельзя интерпретировать как независимо измеренные физические константы. Энергия серии — среднее при устойчивой нагрузке; latency — медиана отдельных синхронизированных запусков, что тоже даёт несовпадение режимов.
